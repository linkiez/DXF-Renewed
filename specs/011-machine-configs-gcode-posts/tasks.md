# Tasks: Machine Configurations and Cutting G-code Post-Processors

**Input**: Design documents from `/specs/011-machine-configs-gcode-posts/`

**Prerequisites**: `plan.md`, `spec.md`, `research.md`, `data-model.md`,
`contracts/machine-config-post-api.md`, `quickstart.md`

**Tests**: Required by the project constitution (Principle III). Every behavior task follows
Red → Green → Refactor: the test task for a behavior is written first and must fail for the expected
reason before the matching implementation task starts.

**Documentation**: Every task that changes a file under `src/` also creates or updates that file's
sibling `.doc.md` (pt-BR, seven sections) in the same task and commit. No other documentation is created
or edited. The three reference documents in `docs/` are read-only evidence.

**Quality gate**: The pre-commit hook runs `yarn test` and `yarn quality:gate`; the gate fails on high
cyclomatic or cognitive complexity and on unused or unresolved files, so functions stay small and every
module is reachable from a barrel or a processor. Never bypass it. To commit a partial set, use
`git stash push --keep-index --include-untracked`, commit, then `git stash pop`. The Phase 2 helpers
(`splitContours`, `arcSweep`, `envelopeIssues`, `releaseIssues`, the barrels) are used only by the processors,
so Phase 2 and User Story 1 are committed together or the gate reports unused exports; every later story is
committed whole.

**Data safety**: Fixtures are synthetic or hand-written. No production program, credential, network map or
log of the analysed project is copied, and no row of the vendor workbook beyond the six listed in the
excerpt task. The library reads no file: configurations, recipes, table rows and plans are supplied as data.

**Organization**: Tasks are grouped by user story. US1 (Talvi) is the MVP. US2 depends on US1's
configuration and processor; US3, US5 and US6 are independent of each other after Phase 2; US4 feeds US3's
program with looked-up settings.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on an incomplete task)
- **[Story]**: User story of the task (US1–US6); Setup, Foundational and Polish have none
- Source paths are under `src/nesting/post/` (`machine/`, `dialects/`, `processors/`, `recipes/`,
  `cutcharts/`); unit tests under `test/unit/nesting/post/`; reviewed programs under
  `test/resources/post-references/`

## Dependencies & Execution Order

### Phase dependencies

- **Setup (Phase 1)**: no dependencies.
- **Foundational (Phase 2)**: depends on Setup and blocks every story. Inside it the order is writer option
  and types first, then messages, validation, frame, envelope, release gate, profile, contour splitter and
  arc helpers, then the shared fixtures and the barrel; the regression run closes the phase.
- **US1 (Phase 3, MVP)**: depends on Phase 2. Its configuration, selector, header and footer, moves, contour
  and processor tasks follow the dependencies written in each task.
- **US2 (Phase 4)**: depends on US1's configuration and processor (the release gate test runs through the
  Talvi processor); the catalog and the `output` field are otherwise independent.
- **US3 (Phase 5)**: depends on Phase 2 and the catalog registry of US2 (`builtInConfigurations.ts`); it does
  not depend on US4 (settings are supplied directly in its tests).
- **US4 (Phase 6)**: depends on Phase 2; its integration task needs US3's processor.
- **US5 (Phase 7)**: depends on Phase 2 and the registry of US2.
- **US6 (Phase 8)**: depends only on Setup (the recipe types, reader and lookup need no shared helper, except the message module of Phase 2 for the issue texts); it can run in parallel with every other story. The 44-file check needs the local folder named by `TALVI_RECIPES_DIR`.
- **Polish (Phase 9)**: depends on the stories it touches; the exports need all three processors, the cut
  chart and the recipe barrels.

### Within each story

- Tests before implementation (Red → Green → Refactor); the test and the implementation of one unit touch
  different files, so a test task marked `[P]` can run beside the tests of other units.
- A dialect module before the processor that uses it; the reference program before the processor.
- The processor task is the story's integration point and ends the story.

### Parallel opportunities

- Phase 2: the test tasks of messages, validation, frame, envelope, release gate, profile, contour
  splitter, arc helpers, the reference plan and the configuration builder are independent files.
- After Phase 2: US1, US3 (after the registry), US5 (after the registry) and US6 can be staffed in parallel;
  US6 needs only the message module of Phase 2.
- Inside a story: the dialect unit tests (selector, frame, moves, contour) are independent.
