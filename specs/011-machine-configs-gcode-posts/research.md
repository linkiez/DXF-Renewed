# Machine Configurations and Cutting Post-Processors Research

Evidence classes used below: **observed** (read from a file of the analysed project), **user-confirmed**
(stated by the user in that project's documents), **inferred** (the project itself marks it so) and
**conflict** (two files disagree). The analysed project is `/home/linkiez/Projetos/pos-processor`
(169 files); credentials, network maps, logs and customer programs in it were not used.

These facts confirm decision D7 (the cut chart block takes its values from a table keyed by material,

## D1. Decision: Extend `src/nesting/post/` instead of a new top-level module

**Rationale:** `MachineProfile` is where machine data enters the post-processing, and it must be able to
carry the configuration. A module outside `post/` would depend on `post/` for the profile and `post/`
would depend on it for the configuration type: a cycle. Keeping configuration, dialects and recipes under
`post/` reuses the registry, the orchestrator, the canonical comparison and the release rules without
changing them.

**Alternatives considered:** A separate `src/nesting/machines/` module (cycle, see above); changing the
existing processors to read the configuration (violates additivity and the reviewed outputs).

## D2. Decision: One `MachineConfiguration` with a source on every critical value

**Rationale:** The analysed project's whole difficulty is knowing which values are real. A value is
`{ value, source }` where `source` has a classification (`observed`, `user-confirmed`,
`vendor-confirmed`, `approved`, `inferred`), a reference to the evidence and, optionally, who confirmed
it. The configuration also holds dialect parameters (the sentinel, the size mask, the head-down and
jump distances, the station selection) as sourced values, so none of them is hidden in code. A value
absent from a configuration is an issue, never a default taken from another machine (FR-011).

**Alternatives considered:** Keeping the data in `MachineProfile.processSettings` (flat primitives, no
source); one configuration file per machine read at run time (the library reads no file).

## D3. Decision: The release gate is a processor validation error

**Rationale:** The orchestrator emits whenever the profile and the pre-emission checks pass and then
adds the processor's validation issues; release needs no error and a matching reviewed output. A
dialect processor returns one `UNAPPROVED_VALUE` error per critical value whose classification is not
`approved`, so the program is still produced for review (FR-012) and is never releasable. Because the
orchestrator already requires an expected output, a release needs both an approved configuration and a
reviewed program. The three built-in configurations start with their values as observed, confirmed or
inferred, so their programs are drafts until a caller supplies an approved copy.

**Alternatives considered:** Refusing to emit at all (hides the program the reviewer needs); a separate
release flag outside the validation issues (a second mechanism for the same rule).

## D4. Decision: The machine frame is a rotation plus a table corner

**Rationale:** Nesting works in a frame with its zero at the bottom left of the sheet. A machine
configuration declares `rotationDegrees` (0, 90, 180, 270 about the sheet) and `origin` (the table
corner that is the machine zero). The mapping is: rotate the sheet so that its long side lies where the
configuration says, which gives a sheet of `W' x H'` with zero at the bottom left; then for origin
bottom-left `X = x'`, `Y = y'`; for bottom-right `X = x' - W'`, `Y = y'`; for top-left `X = x'`,
`Y = y' - H'`; for top-right `X = x' - W'`, `Y = y' - H'`. This reproduces the Talvi's X from -1500 to 0
and Y from 0 to 3000 and replaces the analysed post's expression `Y + extent`. Every mapped point is
compared with the confirmed envelope with `EPSILON`; the controller's soft limits are never the
envelope (D2). The rotation of the Talvi stays inferred (research table above).

**Alternatives considered:** A free affine matrix (more freedom than any machine here needs and harder
to review); mapping inside each dialect (three copies of one rule).

## D5. Decision: Contour-oriented dialects split the plan once

**Rationale:** The Talvi and the GloryStar emit one block per contour with its own start and end. The
cut plan is a flat action list. A contour is the run that starts at the rapid before a `pierce` and ends
before the next rapid (or the `end` action). One internal splitter returns, for each contour, the
rapid, the pierce, the lead-in, cuts, lead-out and overcut, and the length of the rapid that follows it,
so the Talvi can write `#<_NextOneDis>` and the GloryStar can choose the flame-off variant from the same
number. `tab` and `common-line` actions are not in the observed dialects and are reported as unsupported
instead of being flattened.

**Alternatives considered:** A streaming emitter that closes the previous contour at the next rapid (the
analysed post does this and needs state in three procedures); a split per dialect (duplication).

## D6. Decision: Talvi rules come from the real programs, the unknowns from the configuration

**Rationale:** The preparation, the ending, the block order, the number formats (4 decimals with trailing
zeros for axes and arc offsets, 3 decimals for distances and the size), the incremental arc centers, the
single full-circle arc and the sentinel are observed in the real programs and are fixed by the
dialect. The pieces the project calls inferred are configuration data: the process mapping (quality to
`P`, `Q`, with a declared rule for an omitted `Q`), the sentinel, the size mask, the rotation. Without a
mapping entry the program carries a comment where the selector would be and a `PROCESS_MAPPING_MISSING`
error; no selector is invented. Arcs of about 2 degrees or less become lines, as the analysed post does.
`F` words are not emitted: the feed belongs to the controller.

**Alternatives considered:** Emitting the selector `P1 Q1` as a default (the analysed project's own
inference, rejected by FR-005); embedding recipe values (rejected by FR-018).

## D7. Decision: GloryStar and Hypertherm follow their reviewed posts, with the conflicts held open

**Rationale:** Their evidence is the post template and script, not machine programs, so their reference
programs are synthetic and reviewed. Every number the scripts hold becomes a sourced dialect parameter
(head-down distance 100 mm, jump distance 1000 mm, the stations, the kerf table index). The two table
size conflicts are recorded as two observed values and the envelope stays `inferred` until the caller
supplies an approved one; the GloryStar's missing helper script and the controller subprograms are listed
in the configuration as external dependencies that the program calls by name and does not define. The
Hypertherm cut chart takes its values from the supplied process settings (torch type, material code,
current, shield gas, cutting surface, thickness, arc voltage, pierce time, heights) and blocks release
when one is missing (FR-007).

**Alternatives considered:** Choosing one of the conflicting table sizes (would invent a limit);
copying the SigmaNEST scripts (proprietary, and they describe SigmaNEST internals, not this library's
plan).

## D8. Decision: A flat reader for the tool files, no XML dependency

**Rationale:** The 44 files share one machine-written structure: a root, a cutting block of scalar tags,
a list of piercing stages and a few scalar blocks, with 119 distinct tags and no attributes or mixed
content. A reader that walks balanced tags and returns nested maps is about 80 lines and runs in Node
and in browsers. `DOMParser` does not exist in Node; an XML library would be a new runtime dependency,
which Principle V forbids without an ADR. File names carry the thickness, material and nozzle in two
patterns (`<thickness>mm <material> <s|d><nozzle>` and `<nozzle>双<thickness>mm`), and a name that fits
neither is reported instead of guessed. Materials of the second pattern are not in the name and stay
unspecified. The speed unit stays unconfirmed in the catalog.

**Alternatives considered:** `fast-xml-parser` (new dependency); regular expressions per field (breaks on
the repeated piercing stage tags).

## D9. Decision: Reference programs are synthetic, reviewed text

**Rationale:** SC-001 compares canonicalized text with a reviewed program. Each machine has a small
synthetic plan (three contours with a line, an arc and a full circle, a hole before its outline, a long
and a short travel) and an expected program written from the dialect rules and checked against the real
Talvi programs by a structure checker in the test helpers (preparation, ending, contour count, block
order, distances, sentinel, arc radii). No production program is copied.

**Alternatives considered:** Using the real NC files as fixtures (customer geometry, FR-020).

## D10. Decision: Output metadata is additive

**Rationale:** `MachineProgram` gains an optional `output` with the file extension and the line ending of
the configuration; the returned text stays canonical LF text, as today, and a caller that needs CRLF
converts at the file boundary. `GcodeWriter` gains a `trailingZeros` option (default off) because the
Talvi's observed numbers keep their trailing zeros and the writer strips them.

**Alternatives considered:** Returning CRLF text (would break the canonical comparison); formatting
numbers in each dialect (a second number formatter).

## D11. Decision: The Hypertherm cut chart values come from the caller-supplied table

**Rationale:** The post's `G59 V502..V507` and `V600..V604` block is exactly what the vendor workbook
lists per material, thickness and consumable class, so the process settings of the Hypertherm program are
looked up and not typed (FR-024). The library reads no file and ships no vendor data: the host converts
the workbook to rows (one record per row, the workbook's column names, plus the unit marker of the first
cell) and the library imports them, builds an index once (material, thickness, class, toggles) and
answers by exact match (FR-022, FR-023). A thickness or class the table lacks is an absence, never the
nearest one. A unit mismatch with the machine configuration is an error, never a conversion (FR-025). The
separation rules are carried with the entry as information (FR-026).

**Alternatives considered:** Parsing the `.xlsx` in the library (needs a ZIP and XML reader, a new
dependency or a large reader, and file I/O the library does not have); embedding the table (vendor data,
about 7,000 rows); accepting the nearest thickness as the post does for its own lookup (invents values).

## D12. Decision: Axis orientation and home are configuration values; the HyPath manual raises no dialect values

**Rationale:** The manual states that the CNC's X/Y orientation and home position are set in the machine
setups and must agree with the table (FR-027), so for the Hypertherm they are the `frame` of the
configuration and are `inferred` until a person who knows the table approves them. The manual has no
G-code reference, so the Hypertherm dialect parameters stay `observed` from the SigmaNEST post and none is
promoted to `vendor-confirmed` by the manual alone. The EDGE Connect Programmer Reference 809550 does confirm
the codes and ranges, so the dialect parameters it states are `vendor-confirmed` for the EDGE Connect
CNC; that it applies to the HyPath on Phoenix 9.761 is the value a person approves (D13).

**Alternatives considered:** Treating the manual as vendor confirmation of the M-codes (it does not
contain them); assuming the SigmaNEST default zero (bottom left, `311 : 1,0`) as the machine's home.

## D13. Decision: The Hypertherm dialect follows the vendor reference, and the validation uses its ranges

**Rationale:** With the reference in the repository the Hypertherm program is no longer only the SigmaNEST
post's shape. The selection codes are written in the vendor's order (torch, material, current, gas,
thickness, then surface when the entry has it); the post's `V506` before `V507` is recorded as an observed
difference and the vendor order wins because the reference states that the order is a requirement of the
CNC. `G41`/`G42` stay immediately before `M07`; `M08` closes the cut; `G40` cancels the kerf; `V6xx` are
written only to override a cut chart value, in the program units for `V603`. Every `V6xx` range of the
reference becomes a validation (FR-029), and the controller settings the program relies on become
configuration data that the result names (FR-030). `M15`/`M16` are not used.

**Alternatives considered:** Keeping the post's order (contradicts the vendor statement); writing every
`V6xx` always (the reference says they are only for overrides, and the cut chart already holds them); letting
the range checks be advisory (an out-of-range value is rejected or clamped by the CNC, so it is an error).

## D14. Decision: Follow the vendor's ProNest post where it is more specific than the SigmaNEST post

**Rationale:** Hypertherm's own ProNest post is the most authoritative sample of a real EDGE Pro program, and it agrees
with the Programmer Reference. The dialect therefore drops `V506` from the default order, writes the kerf as
`G43 X<kerf>` plus `G41`/`G42` (no kerf table index to guess), does not write zero values for the voltage, the pierce
time or the heights, writes the feed word for each profile, and opens True Hole programs with the vendor comment. The one
point on which the two posts disagree, `G92 X0 Y0`, becomes the configuration value `axisPreset` (inferred, off), because
it changes the meaning of every coordinate and only the shop knows how the operator zeroes the torch.

**Alternatives considered:** Keeping the kerf table call of the SigmaNEST post (needs a table index that nobody has
confirmed); writing `G92` always (changes coordinates if the shop does not zero the torch); omitting the feed word (both
vendor-ecosystem posts write it).
